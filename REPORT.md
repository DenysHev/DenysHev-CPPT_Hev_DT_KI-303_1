# Звіт до лабораторної роботи №4

## 1. Тема, номер і варіант

**Тема:** потокова обробка даних у Java-проєкті.
**Лабораторна робота:** №4.
**Варіант:** 4 — склад автозапчастин.
**ОС розробки:** macOS.
**Технології:** Java 21, Maven, JUnit 5, SpotBugs, GitHub Actions.

Предметна область і номер варіанта з попередніх робіт збережені.

## 2. Мета роботи

Мета роботи — замінити основні обчислення над колекцією декларативними
конвеєрами Stream API, не змінюючи предметну модель, CSV-контракт і попередні
показники звіту.

Досягнуто стану, у якому п'ять потокових запитів і пошук через `Optional`
винесені в окремий клас `InventoryStreamQueries`, перевірені тестами та
підключені до виконання програми.

## 3. Стан до і після роботи

До роботи основні показники складу вже обчислювалися через Stream API, але
окремих запитів варіанта 4 не було. Після роботи додано самостійні конвеєри
для відбору, перетворення, групування, статистики, top-N і пошуку.

Збережено:

- поліморфну модель `SparePart`, `OriginalPart`, `ReplacementPart`;
- `PartKind` і поліморфний `warrantyCost()`;
- CSV із п'ятьма полями;
- кількість коректних записів;
- загальну кількість деталей;
- вартість запасу;
- найдорожчу деталь;
- попередні тести й CLI-аргументи.

## 4. Контракт даних

Один запис має формат:

```text
sku;name;stock;unitPrice;supplier
```

`SparePart` є спільним поліморфним типом із полями `sku`, `name`, `stock`,
`unitPrice` і `supplier`. Порожні обов'язкові поля, від'ємний залишок,
від'ємна ціна, `NaN` та нескінченність відхиляються парсером.

Порогом для запиту відбору зафіксовано `LOW_STOCK_THRESHOLD = 10`.
Умова є строгою: `stock < 10`, тому запис із залишком 10 не потрапляє до
результату.

## 5. П'ять запитів Stream API

Усі запити отримують джерелом `List<SparePart>`. Для кожного виклику
створюється новий потік; вхідна колекція не змінюється.

| Запит | Конвеєр | Collector / terminal operation | Тип результату |
|---|---|---|---|
| Малий залишок | `stream → filter(stock < 10)` | `toList()` | `List<SparePart>` |
| Артикули | `stream → map(SparePart::sku)` | `toList()` | `List<String>` |
| Вартість за виробником | `stream → groupingBy(supplier)` | `summingDouble(stock * price)` | `Map<String, Double>` |
| Статистика цін | `stream → summarizingDouble(SparePart::unitPrice)` | `summarizingDouble` | `DoubleSummaryStatistics` |
| Top-N | `stream → sorted → limit(N)` | `toList()` | `List<SparePart>` |

`groupingBy` використовує `LinkedHashMap`, щоб порядок виробників у
контрольному звіті був відтворюваним.

## 6. Групування та статистика

Ключем групування є `supplier`, а значенням кожної групи — сума `stock *
unitPrice`. Для контрольного набору отримано:

```text
Bosch=23205.00
Mann=6400.00
Sachs=12250.00
NGK=8257.50
```

`priceStatistics` повертає кількість, суму, середнє, мінімум і максимум
`unitPrice`. Для порожнього списку кількість і сума дорівнюють нулю; у звіті
мінімум, максимум і середнє явно форматуються як `0.00`, а не виводяться як
нескінченність або службове значення.

Грошові значення форматуються через `Locale.ROOT` із двома знаками після
коми.

## 7. Компаратор і top-N

Для `topByPrice` використано складений компаратор:

1. `unitPrice` — за спаданням через `reversed()`;
2. `name` — за зростанням через `thenComparing`;
3. `limit(N)` — після повного сортування.

Від'ємний `N` відхиляється через `IllegalArgumentException`, `N = 0`
повертає порожній список, а завеликий `N` повертає всі доступні записи.
Основний контрольний набір має шість записів, тому top-5 перевіряє усікання.

## 8. Optional-пошук

`findBySku` фільтрує записи за артикулом і завершує конвеєр через `findFirst`.
Для дубльованого ключа повертається перший запис у початковому порядку.
Для відсутнього артикулу повертається `Optional.empty()`, який у звіті
виводиться як `не знайдено`; `null` для відсутнього результату не
використовується.

## 9. Еквівалентність реалізацій

| Циклова логіка | Stream API | Результат контрольної перевірки |
|---|---|---|
| Перебрати записи й залишити `stock < 10` | `filter` | `SKU003`, другий `SKU001` |
| Додати кожен `sku` до списку | `map` | 6 артикулів у початковому порядку |
| Накопичувати суму за `supplier` | `groupingBy` + `summingDouble` | 4 групи, ті самі суми |
| Оновлювати count/sum/min/max ціни | `summarizingDouble` | count 6, sum 5995.75, min 275.25, max 2450.00 |
| Вибирати найдорожчі записи вручну | `sorted` + `limit` | ті самі 5 записів у тому самому порядку |
| Перевіряти знайдений запис або `null` | `findFirst` + `Optional` | перший `SKU001` або порожній результат |

Порівнювалися не кількість рядків, а умови, порядок сортування, агрегати,
дублікати, порожні результати та незмінність джерела. Нові тести містять
очікувані результати, отримані для того самого контрольного набору.

## 13. Порівняння циклової та потокової реалізацій

Потокова реалізація відокремлює умову відбору, перетворення, агрегацію та
порядок сортування. Це робить кожен запит незалежним і дозволяє додавати нові
запити без спільного змінного акумулятора.

Циклова реалізація могла б бути коротшою для одного агрегату, але змішувала
б умову, стан акумулятора та формат результату. Перевага Stream API тут не
в кількості рядків, а в явному порядку операцій і можливості перевіряти кожен
запит окремо. Для малого набору даних продуктивність не робилася критерієм
вибору; `parallelStream()` не застосовувався через відсутність потреби та
малий обсяг даних.

## 15. Відповіді на контрольні питання

1. **Чим потік відрізняється від колекції?** Колекція зберігає елементи, а
   потік описує обчислення над джерелом і не є контейнером.
2. **Які частини має конвеєр?** Джерело, проміжні операції та кінцеву
   операцію.
3. **Чому проміжні операції ліниві?** Вони лише будують конвеєр і
   виконуються після виклику terminal operation.
4. **Що робить `filter`?** Залишає елементи, для яких `Predicate` повертає
   `true`.
5. **`map` і `mapToDouble`?** `map` перетворює на об'єктний тип, а
   `mapToDouble` створює числовий `DoubleStream` без зайвого пакування.
6. **Для чого `distinct`?** Для видалення дублікатів за `equals` і
   `hashCode`; у цій роботі дублікати навмисно зберігаються для перевірки
   `findFirst`.
7. **Чому `sorted().limit()` не те саме, що `limit().sorted()`?** Перша
   форма вибирає top-N з усієї колекції, друга сортує лише перший префікс.
8. **Роль terminal operation?** Вона запускає лінивий конвеєр і повертає
   результат або виконує кінцеву дію.
9. **Коли `joining`?** Коли елементи потрібно об'єднати в один рядок із
   роздільником, префіксом або суфіксом.
10. **Як працює `groupingBy`?** Обчислює ключ для кожного елемента та
    розподіляє елементи по відповідних групах карти.
11. **Як отримати суму групи?** Передати downstream collector
    `Collectors.summingDouble(...)` або `summingInt(...)`.
12. **Що містить `DoubleSummaryStatistics`?** Кількість, суму, середнє,
    мінімум і максимум.
13. **Статистика порожнього потоку?** Count і sum дорівнюють нулю, average,
    min і max мають службові значення; звіт явно нормалізує їх до `0.00`.
14. **Як утворюється складений компаратор?** Через ланцюжок
    `Comparator.comparing...().thenComparing(...)`.
15. **Чому `reversed()` до `thenComparing`?** Так змінюється лише основний
    ключ, а другий критерій залишається зростаючим.
16. **Що вирішує `Optional`?** Явно представляє наявність або відсутність
    результату без повернення `null`.
17. **`orElse`, `orElseThrow`, `ifPresent`?** Вони відповідно задають
    запасне значення, вимагають результат або виконують дію лише за наявності.
18. **Чому небажаний зовнішній список у `forEach`?** Це прихований змінний
    стан, який погіршує читабельність, тестування та безпечність паралельної
    обробки.
19. **Що перевіряти під час рефакторингу?** Значення, порядок, дублікати,
    порожній вхід, крайові умови, побічні ефекти та винятки.
20. **Коли виправданий паралельний потік?** Для великих незалежних обсягів
    даних із достатньо дорогою обробкою та потокобезпечними операціями; для
    цього малого набору він не потрібен.
